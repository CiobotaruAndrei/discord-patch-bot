### Changed

- Zero exceptii de comentarii in cod (regula 1, finisaj pentru nota maxima): cele doua note scurte de race-condition din `cron.ts` au fost eliminate din cod, iar rationale-ul lor (ordinea „re-armeaza heartbeat-ul doar cat timp `currentCronToken === lockToken`" si „invalideaza tokenul inainte de `stopHeartbeat`/`releaseDbLock`") a fost mutat complet in `src/docs/CONTEXT_REPO_CLEAN.md`. Allowlist-ul din `scripts/check-no-comments.ts` este acum gol — checker-ul nu mai accepta nicio exceptie, deci orice comentariu din `.ts`/`.js`/`.rs` esueaza CI. Test actualizat in `checkNoComments.test.ts` (`ALLOWED_COMMENTS` gol, `isAllowed` respinge orice).
- Mod strict optional pentru recovery-verify outbox + observabilitate config: (1) `NOTIFICATION_OUTBOX_RECOVERY_STRICT=true` (implicit oprit) schimba comportamentul cand verificarea pe istoricul canalului esueaza (nu poate citi mesajele): in loc de fail-open (trimite oricum, cu risc de duplicat), face fail-closed — **nu** trimite, reprogrameaza jobul cu backoff (ramane in coada) si numara `recoveryFailures` (care declanseaza si admin alert-ul `outbox:recovery-read`). Util pe servere unde duplicatele sunt foarte grave; implicit ramane fail-open ca sa nu blocheze livrarile la un hiccup tranzitoriu de permisiuni. (2) Metrica noua `bot_outbox_recovery_verify_enabled_guilds` (gauge) arata cate servere au activat protectia maxima per-guild (`outboxRecoveryVerify`), refresh-uita la fiecare drain din `countDocuments`. (3) S-a eliminat un comentariu din `notificationOutbox.ts` (catch-ul `E11000`) care incalca regula „fara comentarii in cod"; rationamentul ramane in acest changelog si in documentatie. Acoperit de teste in `outboxDelivery.functional.test.ts` (strict: fetch esuat -> fail-closed + recoveryFailed, marker gasit -> nu retrimite, istoric citit fara marker -> trimite), `notificationOutbox.test.ts` (strict ok:false+recoveryFailed -> recoveryFailures + reprogramare) si `outboxWorker.test.ts` (gauge `outboxRecoveryVerifyEnabledGuilds`).
- Robustete suplimentara outbox (dedupe la nivel de coada + alerte operationale): (1) colectia `notificationOutbox` are acum un index unic *sparse* pe `dedupeKey`, iar `enqueueOutbox` prinde explicit eroarea de cheie duplicata (`E11000`) si nu mai duplica un job pending cu acelasi continut — protectia anti-duplicat nu mai depinde doar de verificarea `notificationOutboxSent` (care acopera doar livrarile deja facute), ci si de unicitatea la nivel de coada pentru joburile in asteptare. (2) `markSent` intoarce acum un boolean: cand marcarea in istoricul de dedupe esueaza (chiar si dupa `withMongoRetry`), drenarea numara esecul intr-o metrica noua `bot_outbox_mark_sent_failures` in loc sa-l inghita silentios — vizibilitate pe fereastra de risc `send` -> `markSent` (un mesaj trimis dar nemarcat poate fi re-trimis la recovery). (3) Worker-ul de drenare trimite un admin alert (cu cooldown per-tip) cand un drain raporteaza `recoveryFailures > 0` (`outbox:recovery-read` — lipseste permisiunea Read Message History pe canalele de notificari) sau `markSentFailures > 0` (`outbox:mark-sent` — risc de duplicare), ca operatorul sa afle proactiv, nu doar din metrici. Acoperit de teste in `notificationOutbox.test.ts` (markSent esuat -> `markSentFailures`, enqueue ignora `E11000` dar propaga alte erori), `outboxWorker.test.ts` (metrica `outboxMarkSentFailures` + alertele pe recoveryFailures/markSentFailures) si literalele de metrici din `cronController.test.ts` / `httpServerRouting.functional.test.ts`.
- Fix critic + finisaje recovery-verify outbox: (1) campul `recoveryVerify` este acum declarat in schema `notificationOutbox` — fara el, Mongoose (strict mode) il stergea la salvare, deci override-ul per-guild nu era persistat (job-ul ajungea fara flag in DB); acoperit de un test fara DB pe modelul real (`outboxSchemaPersistence.functional.test.ts`) care prinde exact aceasta scapare (strict mode sterge campurile nedeclarate). (2) Limita de mesaje scanate la verificarea pe istoric este configurabila prin `NOTIFICATION_OUTBOX_RECOVERY_HISTORY_LIMIT` (implicit 25; min 5, max 100), in loc de 25 fix — util pe canale aglomerate. (3) Metrica noua `bot_outbox_recovery_marker_missing` numara cazurile in care fetch-ul de istoric a reusit dar marker-ul nu a fost gasit si mesajul a fost re-trimis (separat de `bot_outbox_recovery_verify_failures` = fetch esuat), pentru debugging „nu am putut verifica" vs „am verificat, dar nu era acolo".
- Recovery-verify outbox finisat: (1) logica de livrare a fost extrasa din `notifications/index.ts` intr-un modul testabil `outboxDelivery.ts` (`createOutboxDelivery`), cu teste de integrare pe `deliver` (canal lipsa/permisiuni, send esuat, verify off, job proaspat, recovery cu/ fara marker in istoric, esec de fetch, override per-guild) in `outboxDelivery.functional.test.ts`; (2) metrici dedicate la `/metrics` — `bot_outbox_recovery_duplicates_prevented`, `bot_outbox_recovery_history_fetches`, `bot_outbox_recovery_verify_failures` — propagate din rezultatul fiecarui drain catre `BotMetrics`; (3) flag-ul de recovery-verify este acum configurabil **per-guild** prin `GuildSettings.outboxRecoveryVerify` (transmis pe job la enqueue), cu fallback la flag-ul global `NOTIFICATION_OUTBOX_RECOVERY_VERIFY`. Acoperit de teste in `outboxDelivery.functional.test.ts`, `notificationOutbox.test.ts`, `outboxWorker.test.ts` (metrici recovery) si `resolveOutboundChannel.test.ts` (passthrough per-guild).
- Verificare optionala pe istoricul canalului la recovery (pentru fereastra rara `send` -> `markSent`), activabila prin `NOTIFICATION_OUTBOX_RECOVERY_VERIFY=true` (implicit oprita). Cand e activa, fiecare embed trimis prin outbox primeste un marker scurt `dedupeKey` in footer, iar un job re-revendicat (contorul `deliveries > 1`, deci o posibila reluare dupa crash) verifica intai ultimele ~25 de mesaje din canal pentru acel marker si, daca il gaseste, considera livrarea deja facuta si nu re-trimite. Foloseste Discord ca sursa de adevar pentru cazul in care procesul a cazut dupa `send` dar inainte de a scrie in istoric. Implicit ramane oprita fiindca adauga un footer vizibil pe fiecare notificare + un fetch de mesaje la fiecare recovery; este un opt-in pentru cine vrea protectie maxima. Helper-ele de marcare/cautare sunt pure si acoperite de teste in `notificationOutbox.test.ts` (`applyDedupeMarker`, `messageHasDedupeMarker`, `$inc deliveries` la claim).
- Intarirea deduplicarii outbox: `dedupeKey` foloseste acum SHA-256 (din `crypto`) peste un payload normalizat stabil (chei sortate recursiv), in loc de un hash FNV pe 32 de biti pe `JSON.stringify` — fara coliziuni practice si independent de ordinea cheilor. TTL-ul istoricului de livrari (`notificationOutboxSent`) este configurabil prin `NOTIFICATION_OUTBOX_SENT_TTL_HOURS` (implicit 24h, in loc de 1h fix; min 1, max 168), ca recovery-ul dupa un crash/deploy lung sa fie acoperit. In plus, marcarea „trimis" (`markSent`) ruleaza acum prin `withMongoRetry`, deci un hiccup tranzitoriu de Mongo nu mai pierde marker-ul intre trimitere si stergerea jobului (strat suplimentar de protectie pe fereastra `deliver` -> `markSent`). Acoperit de teste in `notificationOutbox.test.ts` (dedupeKey SHA-256 stabil la chei reordonate).
- Outbox cu deduplicare idempotenta: fiecare job primeste un `dedupeKey` stabil (hash din guildId+channelId+kind+payload) si exista un istoric scurt de livrari (`notificationOutboxSent`, index unic pe `dedupeKey`, TTL 1h). `enqueueOutbox` nu mai pune un job daca acel `dedupeKey` a fost livrat recent (enqueue idempotent), iar la drenare, daca un job revendicat are deja `dedupeKey` in istoric, este sters fara re-trimitere (recovery dupa un crash intre `send` si `delete`). Discord nu permite exact-once real, dar impreuna cu lease-ul (care elimina duplicatele concurente) fereastra de duplicare la crash este redusa la intervalul dintre trimiterea pe Discord si scrierea in istoric. Acoperit de teste in `notificationOutbox.test.ts` (dedupeKey pe job, enqueue idempotent, inregistrare la livrare, recovery fara re-trimitere).

- Drenarea outbox-ului revendica acum job-urile printr-un lease atomic (`findOneAndUpdate` care seteaza `lockedUntil` / `lockedBy`) inainte de livrare, in loc de `find` + procesare. Doua drenari care s-ar suprapune (de ex. daca lock-ul `outbox_drain` ar expira mid-drain) nu mai pot livra acelasi job de doua ori — corectitudinea nu mai depinde de TTL-ul lock-ului. La reincercare lease-ul este eliberat (`$unset lockedUntil/lockedBy`), iar la crash dupa trimitere fereastra de duplicare este marginita de durata lease-ului (Discord nu permite exact-once real). S-au adaugat metrici de latenta si vechime: `bot_outbox_delivery_ms_total` (suma duratelor de livrare; cu `bot_outbox_sent` da latenta medie), `bot_outbox_oldest_job_age_seconds` (vechimea celui mai vechi job din coada) si `bot_outbox_lock_acquire_failures` (cate drenari au fost sarite fiindca lock-ul era detinut de alta instanta). Comentariul explicativ introdus anterior in `outboxWorker.ts` a fost scos (regula „fara comentarii in cod"); rationamentul ramane in acest changelog si in documentatie. Acoperit de teste in `notificationOutbox.test.ts` (lease + release) si `outboxWorker.test.ts` (metrici latenta/vechime/lock-fail).

Acoperit de teste in `outboxWorker.test.ts` (metrici + scalarea TTL) si `notificationOutbox.test.ts` (`queued`).

Dual-read-ul defensiv pe campurile legacy a fost scos din ambele servicii (cron-ul de reduceri pre-filtreaza prin colectie via `loadSeenDiscountHashes`, iar la update-uri claim-ul atomic ramane verificarea autoritara). `buildPendingUpdatesQueue` nu mai citeste `guild.seen`, iar helper-ul mort `getSeenSet` a fost eliminat. Migrarile `m5`/`m6` (backfill) si `m7` (`$unset` legacy) raman pentru a converti datele existente la prima pornire. Acoperit de teste in `seenRepository.functional.test.ts` (seed + claim), `subscriptionInteractions.functional.test.ts`, `pendingUpdatesQueue.functional.test.ts`, `notificationServices.functional.test.ts` si E2E.
- Outbox-ul de notificari este drenat acum de un worker dedicat, pe propriul interval, nu doar o data la finalul fiecarui ciclu cron. `createOutboxWorker` (`app/scheduler/outboxWorker.ts`) ruleaza un timer independent, configurabil prin `NOTIFICATION_OUTBOX_DRAIN_INTERVAL_MS` (implicit 15000ms; min 2000, max 600000), protejat de un lock Mongo dedicat (`outbox_drain`) ca instantele multiple sa nu trimita dublu. Astfel, pe volum mare de notificari sau multe retry-uri, backlog-ul nu mai asteapta cadenta lenta a cron-ului (10-60 min) ci se goleste rapid. Drenarea per ciclu cron a fost eliminata (decuplare completa intre detectie si trimitere). Worker-ul porneste in handler-ul `ready` doar cand `NOTIFICATION_OUTBOX_ENABLED=true` si se opreste curat la shutdown. Acoperit de teste in `outboxWorker.test.ts` si `outboxWiring.functional.test.ts`.
- Claim-ul `seen` (update-uri si reduceri) nu mai scrie pe documentul guild-ului: guard-ul de abonament a devenit un read (`GuildModel.exists`), iar singura scriere ramasa este upsert-ul atomic in colectia dedicata (`guildSeenUpdates` / `guildSeenDiscounts`). Astfel dispare riscul de stare partiala in care update-ul pe guild reusea, dar upsert-ul in colectia `seen` esua. Scoaterea din `pendingUpdates` / `pendingDiscounts` si `lastProcessedGameKey` se persista oricum in `$set`-ul final al serviciului (care reconstruieste complet cozile din coada in memorie), deci eliminarea lor din claim nu pierde nimic. Acoperit de teste in `seenRepository.functional.test.ts` si E2E.

Claim-ul devine un upsert atomic in colectie (matchedCount din `upsertedCount`), iar guard-ul de abonament + scoaterea din `pendingUpdates` + `lastProcessedGameKey` raman pe documentul guild-ului — deci documentul nu mai creste cu istoricul `seen`. Dedup-ul face dual-read: serviciul sare item-urile aflate in map-ul legacy `seen` de pe documentul guild, iar colectia previne re-trimiterea prin index-ul unic, astfel incat o migrare incompleta nu poate produce re-notificari (spam). Migrarea `m6` backfilleaza map-ul legacy `seen` in colectie. `pendingUpdates` si `pendingDiscounts` raman deocamdata pe documentul guild-ului (faza urmatoare). Acoperit de teste in `seenRepository.functional.test.ts`, `mongoMigrations.functional.test.ts` si E2E.
- Istoricul `seen` pentru reduceri a fost mutat intr-o colectie dedicata `guildSeenDiscounts`, cu index unic `{ guildId, dealHash }`, in loc sa fie un array tot mai mare pe documentul guild-ului (primul pas din migrarea catre colectii separate pentru scalare). Claim-ul devine un upsert atomic in colectia dedicata (matchedCount din `upsertedCount`), iar guard-ul de abonament + scoaterea din `pendingDiscounts` raman pe documentul guild-ului. Verificarea „deja vazut" face dual-read: citeste si array-ul legacy `seenDiscounts`, si colectia, astfel incat o migrare incompleta nu poate produce re-notificari (spam). Acoperit de teste in `seenRepository.functional.test.ts`, `mongoMigrations.functional.test.ts` si E2E.
- Fetch-ul de update-uri foloseste acum concurrency separat pe sursa, nu o singura coada globala. Jocurile sunt grupate dupa sursa (Steam, Epic, listing, drivere Nvidia/AMD/Intel, restul), iar fiecare grup ruleaza in paralel cu propria limita (`FETCH_CONCURRENCY_STEAM`=4, `FETCH_CONCURRENCY_EPIC`=2, `FETCH_CONCURRENCY_LISTING`=8, `FETCH_CONCURRENCY_DRIVER`=2, restul pe `FETCH_CONCURRENCY`). Astfel o sursa lenta nu mai blocheaza tot ciclul cron, iar fiecare sursa poate fi reglata dupa cat de sensibila e la rate limit. Rezultatele raman aliniate la ordinea de intrare. Acoperit de teste in `perSourceConcurrency.test.ts`.
- Conditional GET (ETag / Last-Modified) pentru sursele de update-uri cu un singur fetch (Steam, Minecraft, Roblox, Nvidia). Clientul HTTP expune `conditionalGet(url, parse)`: tine minte `etag` / `last-modified` per URL si trimite `If-None-Match` / `If-Modified-Since` la urmatorul check; daca serverul raspunde `304 Not Modified`, reuseaza rezultatul parsat anterior fara sa redescarce sau sa reparseze corpul. `httpReq` accepta acum `acceptNotModified`, astfel incat un `304` nu mai e tratat ca eroare. Inofensiv cand serverul nu suporta validatori (face un GET normal). Acoperit de teste in `conditionalGet.test.ts`.
- Trimiterile catre Discord sunt acum grupate: in loc de cate un mesaj per update/reducere, fiecare guild primeste un singur mesaj cu pana la 10 embed-uri (limita Discord) pe trimitere, in pachete pana la `MAX_UPDATES_PER_CYCLE` / `MAX_DEALS_PER_CYCLE`. Reduce numarul de request-uri Discord, latenta si presiunea pe rate limit. Itemii sunt claim-uiti (`seen`) inainte de trimitere; daca un mesaj esueaza, tot pachetul lui se face rollback si re-coadeaza (sau intra in dead-letter la epuizarea reincercarilor), iar ping-ul de rol apare o singura data, pe primul mesaj. Acoperit de teste in `notificationServices.functional.test.ts`.
- Cron-ul are acum jitter si cycle budget. `CRON_JITTER_MS` adauga un offset aleator (+/-) la fiecare programare a urmatorului ciclu, ca instantele multiple sa nu se trezeasca simultan si sa se loveasca pe lock-ul Mongo. `CRON_CYCLE_BUDGET_MS` (implicit un `CRON_INTERVAL_MS`) face ca, daca un ciclu dureaza prea mult, urmatorul sa sara peste reduceri o data pentru recuperare (backpressure soft). `.env.example` include si preset-uri de tuning recomandate pentru bot mic/mediu si multe servere. Acoperit de teste in `cronController.test.ts`.
- Faza de dispatch (cron) este acum rezistenta la caderea fetch-ului prin event store: daca `getLatestForAllGames` (update-uri) sau `fetchDeals` (reduceri, per moneda) esueaza, in loc sa abandoneze ciclul / sa sara guild-ul, dispatch-ul citeste ultimul snapshot persistat (`loadFetchSnapshot` — `updates` respectiv `deals:<MONEDA>`) si continua trimiterile de pe ultimele date bune. Deduplicarea `seen` previne re-trimiterea, iar TTL-ul snapshot-ului limiteaza vechimea; daca nu exista snapshot, comportamentul ramane cel vechi (abandon/skip). Astfel dispatch-ul nu mai depinde de un fetch reusit in acel moment. Acoperit de teste in `fetchSnapshots.functional.test.ts`.

### Fixed

- `buildDealEmbed` limiteaza procentul de reducere la intervalul `[0, 100]`; un snapshot `pendingDiscounts` corupt sau reluat (de ex. `savings: 999`) nu mai poate afisa valori imposibile precum `reducere de 999%`.
- Fallback-ul TypeScript `extractDateScore` (folosit cand addon-ul Rust nu este compilat) scaneaza acum tot URL-ul dupa prima data `YYYY-MM-DD` valida, identic cu implementarea Rust. Anterior se uita doar la prima potrivire de tipar; daca aceasta avea un an/luna/zi in afara intervalului (de ex. un an de arhiva `1999-...` sau un grup numeric `5566-77-88` inaintea datei reale), intorcea `0` si nu mai cauta o data valida ulterioara, ceea ce putea face ca sortarea candidatilor `listing_based` dupa data sa aleaga articolul gresit drept „cel mai recent”.

### Security

- Comenzile administrative au verificari runtime de administrator in handler-ele sensibile, pe langa permisiunile slash command declarate.
- Endpoint-ul `/metrics` poate fi protejat cu token si comparatie `timingSafeEqual`.
- Workflow-ul de dependency review poate bloca PR-uri cand Dependency Graph este disponibil.
- Dependabot este configurat pentru actualizari npm si GitHub Actions.
- Clientul HTTP valideaza hosturile prin URL + DNS/IP inainte de request si prin lookup-ul agentului, pentru protectie SSRF mai stricta.
