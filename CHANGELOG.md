## [Unreleased]

### Fixed

- **`/latest updates` foloseste acum snapshot-ul persistat cand fetch-ul live pica, simetric cu `/latest reduceri` si cu cron-ul (review #449 #1)**. Pana acum, daca `getLatestForAllGames` arunca, handler-ul manual `/latest updates` afisa direct o eroare (`Nu am reusit sa obtin update-urile`), desi cron-ul si `/latest reduceri` au de mult fallback pe snapshot. Acum handler-ul incearca `loadFetchSnapshot("updates")` + `validateUpdateFetchSnapshot` (acelasi event-store + acelasi validator ca cron-ul, prag de prospetime 60 min), iar daca gaseste un snapshot proaspat il foloseste cu un banner clar (`OK: Update-uri incarcate din ultimul snapshot salvat (fetch-ul live a esuat) - vechime ~N min.`) + un `WARN`; fara snapshot proaspat, eroarea ramane explicita. `validateUpdateFetchSnapshot` era deja expus pe runtime de `attachUtilities` (langa `validatePendingDiscountSnapshot`). Acoperit de `latestInteractionHandler.functional.test.ts` (fetch picat + snapshot proaspat -> banner; fetch picat + fara snapshot -> eroare explicita).
- **Worker-ul outbox e acum fail-CLOSED daca citirea flagului de pauza esueaza (review #449 #2)**. `drainTick` folosea `isPaused().catch(() => false)`, deci o eroare tranzitorie la citirea starii de pauza (Mongo/flag) era tratata ca "nu e pe pauza" si botul **continua sa drenze** — fail-open pentru o comanda operationala de siguranta (`/outbox pause`). Acum, daca `isPaused()` arunca, worker-ul **sare ciclul** (nu atinge lock-ul, nu drenza), logheaza `WARN` si incrementeaza metrica noua `bot_outbox_pause_check_failures` (vizibila in `/metrics`), ca operatorul sa vada esecurile de citire. Acoperit de `outboxWorker.test.ts` (pauza neclara -> fail-closed: 0 acquire, 0 drain, metrica +1).
- **`validatePendingDiscountSnapshot` intoarce acum un tip validat real pentru snapshot-urile de reduceri.** `DealInfo.savings` era declarat doar `number`, dar validatorul accepta corect si string-uri numerice din snapshot-uri persistate; type guard-ul promitea deci o forma mai ingusta decat runtime-ul. `DealInfo.savings` este acum `PriceValue`, iar validatorul narrow-uie la `ValidatedDealInfo` cu `title`, `store`, `link`, preturi si `savings` obligatorii. Gard nou in `auditFixesMay26.test.ts` verifica narrowing-ul pe `savings: "33"`; documentat in `src/docs/CONTEXT_REPO_CLEAN.md` si `src/docs/FUNCTION_MAP_CLEAN.md`.

- **`/outbox drain-now` respecta pauza globala a outbox-ului, nu o mai ocoleste manual.** Comanda verifica `getOutboxPaused()` inainte sa revendice lock-ul `outbox_drain`; daca drenarea este pe pauza, raspunde explicit ca trebuie rulat `/outbox resume` si nu ia lock-ul / nu porneste drain-ul. Astfel pauza folosita in mentenanta sau incident response ramane autoritara si pentru drenarea manuala. Acoperit de `outboxAdminHandler.functional.test.ts`; documentat in `README.md`, `OPERATIONS.md`, `docs/Comenzi Functionalitate.md` si `src/docs/CONTEXT_REPO_CLEAN.md`.
- **Workflow-ul de release foloseste o singura sursa pentru body-ul GitHub Release.** `release.yml` pasa simultan `body_path: release-notes.md` si `generate_release_notes: true` catre `softprops/action-gh-release`, deci release-ul combina notele extrase din `CHANGELOG.md` cu notele generate automat de GitHub. Eliminat `generate_release_notes`; body-ul publicat vine determinist din `release-notes.md`, extras din sectiunea tag-ului. Gard nou in `releaseGate.test.ts` ca cele doua moduri sa nu mai apara impreuna. Documentat in `README.md` si `RELEASING.md`.

### Security

- **`Dependency Audit` (`npm audit` + `cargo audit`) ruleaza acum si pe PR-urile care schimba lockfile-urile, nu doar manual/schedule (review manual R12 #2)**. Workflow-ul `dependency-audit.yml` avea doar `workflow_dispatch` + `schedule` (saptamanal), desi continea `npm audit --omit=dev --audit-level=moderate` si `cargo audit --deny warnings` — deci un PR care introducea o dependenta vulnerabila trecea neauditat pana la urmatorul scan programat. Adaugat trigger `pull_request` cu filtru `paths` pe `src/package.json` / `src/package-lock.json` / `src/native/Cargo.toml` / `src/native/Cargo.lock`, deci auditul devine un check blocant exact pe PR-urile care ating arborele de dependente (npm sau cargo), fara sa ruleze inutil pe PR-uri care nu schimba deps. Acoperit de `supplyChainConfig.test.ts` (garda: workflow-ul are `pull_request` pe caile de lockfile + contine `npm audit`/`cargo audit`).
- **Pin pe versiunile patch-uite ale `undici` prin overrides scoped (deblocheaza gate-ul Trivy)**. Trivy (CI-ul `scan`, blocheaza pe CRITICAL/HIGH **fixabile**) a inceput sa semnaleze CVE-uri HIGH in `undici`: `cheerio@1.2.0 -> undici@7.27.2` avea **trei** (`CVE-2026-12151` DoS prin memorie nemarginita, `CVE-2026-6734` info-disclosure/data-integrity, `CVE-2026-9697` MITM prin TLS ignorat), iar `discord.js@14.26.4` / `@discordjs/rest -> undici@6.24.1` avea `CVE-2026-12151`. Fiindca cele doua consumatoare cer linii majore diferite de undici (cheerio pe 7.x, discord.js pe 6.x), s-au folosit **overrides imbricate (per-parinte)** in `src/package.json`: `cheerio.undici >=7.28.0 <8` (-> `7.28.0`, fixeaza toate trei) si `discord.js.undici >=6.27.0 <7` (-> `6.27.0`, fixeaza CVE-2026-12151 fara sa forteze discord.js pe 7.x, care i-ar strica clientul REST). `package-lock.json` regenerat, `npm audit` 0 vulnerabilitati, build + suita completa (854) raman verzi. Garda din `supplyChainConfig.test.ts` pinuieste acum si cele doua override-uri de undici.
- **`/health` e adaugat si in guard-ul runtime `ADMIN_COMMANDS` (defense-in-depth peste `setDefaultMemberPermissions`, review manual R5 #1)**. PR-ul anterior a restrictionat `/health` doar la nivel de slash command (`setDefaultMemberPermissions`); daca permisiunea declarata e ocolita sau gresit configurata in Discord, protectia nu mai exista. Adaugat `"health"` in `ADMIN_COMMANDS` din `adminCommandRouterGuard.ts`, deci `/health` trece acum si prin `requireGuildAdmin` la runtime (ca `/start`/`/stop`/`/set`/`/outbox`) — un membru fara Administrator primeste raspunsul ephemeral de refuz inainte sa ajunga la handler. Acoperit de `adminGuard.test.ts` (`isAdminProtectedCommand` e true pentru `start`/`stop`/`set`/`outbox`/`health` si false pentru `ping`/`games`/`help`/`report`/`history`/`latest`). Documentat in `README.md`.
- **`/health` e acum restrictionat la Administrator (`setDefaultMemberPermissions`), nu mai e public (review manual Medium)**. Comanda raporteaza stare interna a infrastructurii (conexiune Discord, MongoDB, cache, uptime) — informatie operationala care nu trebuie expusa oricarui membru al unui server. Definitia din `slashCommandDefinitions.ts` nu seta nicio permisiune default, deci `/health` era vizibila si rulabila de toata lumea. Adaugat `.setDefaultMemberPermissions(PermissionsBitField.Flags.Administrator.toString())`, identic cu `/start`/`/stop`/`/set`. Acoperit de `slashCommandDefinitions.functional.test.ts` (comenzile admin `start`/`stop`/`set`/`health` poarta flag-ul Administrator; `ping`/`games`/`help`/`report` raman publice). Documentat in `README.md`.
- **Pin pe versiunile patch-uite ale dep-urilor tranzitive `form-data` si `ws` (deblocheaza gate-ul Trivy)**. Baza de date Trivy (CI-ul `scan`, gate care blocheaza pe CRITICAL/HIGH **fixabile**) a inceput sa semnaleze doua CVE-uri HIGH proaspat fixabile: `form-data` **CVE-2026-12143** (4.0.5, tranzitiv via `axios`) si `ws` **CVE-2026-48779** (8.20.1, DoS prin memory exhaustion din fragmente mici, tranzitiv via `discord.js`/`@discordjs/ws`). Adaugat `overrides` in `src/package.json` (`form-data >=4.0.6`, `ws >=8.21.0`) si regenerat `package-lock.json` -> rezolva `form-data@4.0.6` + `ws@8.21.0`, `npm audit` 0 vulnerabilitati. Pin-urile sunt patch-uri compatibile (acelasi major), build + suita completa (826) raman verzi. Garda noua in `supplyChainConfig.test.ts` pinuieste prezenta override-urilor ca sa nu regreseze.
